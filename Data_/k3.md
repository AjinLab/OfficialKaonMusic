# Kaon Music — Initial Architectural Assessment

No code below. This is the structural analysis you asked for, organized per your nine requested outputs.

## 1. Analysis of the Vision and Requirements

Stripping the vision down to what is load-bearing:

- **"Music belongs to the user"** translates architecturally into three concrete obligations: (a) no required accounts or services, (b) user data — favorites, history, playlists — must survive file renames, moves, and MediaStore churn, and (c) failures in optional subsystems (artwork, metadata quirks) must never damage the core experience. This is the vision's real architectural content, and it primarily drives the **identity decision** (§8, D2).
- **Playback reliability** drives the service/facade split and the single-source-of-truth rule.
- **"Fast on modest hardware with large libraries"** drives the sync design, artwork strategy, and list-rendering decisions — and it is a *measurement* requirement, not a license to pre-optimize.
- Everything else — enrichment, recommendations, deep customization, streaming — is explicitly directional. The brief itself says this; the architecture should take that seriously.

Honest assessment: the requirements are unusually well-specified. The biggest risks are not technical unknowns — they are **scope inflation** and **premature abstraction**, both of which your own brief warns against. My job is mostly to hold that line.

## 2. Contradictions, Ambiguities, and Risks

**Contradictions / tensions:**

1. **"Avoid competing sources of truth" vs. queue persistence + history.** You already flagged this, but it needs an explicit ownership rule, not just a principle (resolved in D3/D4 below).
2. **MediaStore ID instability vs. durable user data.** MediaStore IDs are *usually* stable across renames/moves on the same volume, but not guaranteed across volumes or provider rebuilds. If favorites/playlists reference MediaStore IDs directly, they will silently rot. This is the sharpest contradiction in the brief and must be resolved before schema design.
3. **"Highly customizable UI" vs. "maintainable, avoid complexity."** Resolve by fixing v1 customization to design tokens (light/dark/accent). Anything beyond that is deferred, explicitly.
4. **"Metadata normalized, not raw" vs. v1 capacity.** "Normalization" must be scoped narrowly for v1: a clean relational schema, case-folded sort keys, and display fallbacks for missing fields. An enrichment pipeline is not v1.
5. **"Large local libraries" vs. the stack table.** Paging 3 is absent from your stack. Either full-list queries are fast enough (plausible up to tens of thousands of tracks — must be measured) or Paging is added. This is a stack gap, not yet a decision.

**Ambiguities / missing decisions you didn't list:**

- **minSdk is unspecified.** You fixed compile/target SDK 36 but not the floor. This is blocking: it shapes MediaStore sync, artwork (platform thumbnail API is 29+), and permission code paths. See D1.
- **Permissions & notification policy.** READ_MEDIA_AUDIO (33+), legacy storage permission (≤32), POST_NOTIFICATIONS (33+, required for the playback notification to be visible), FOREGROUND_SERVICE_MEDIA_PLAYBACK (34+). Needs a version-policy decision, not invention.
- **Logging & crash reporting.** No logging library in the stack, and crash reporting conflicts with the "private" identity unless it's opt-in. Open decision.
- **Navigation 3 maturity.** I cannot verify its stability status as of today from here. Before building core flows on it, confirm its current release state and adoption. The decision is cheap to reverse *only if* the screen count stays small.
- **The player is not a destination.** A persistent mini-player with an expandable full player is an overlay concern, not a back-stack concern. This tension exists regardless of which navigation library you pick. Don't let the nav library's destination model swallow the player UI.

**Risks (technical):**

- **MediaController connection lifecycle** — leaks and cold-start races are the most common real-world bug source in Media3 apps. Mitigated by a single process-scoped facade (D3).
- **Sync correctness** — duplicates after rename, zombie entries after deletion. Mitigated by making sync idempotent by construction (D5).
- **Queue restore races** — user taps play before restore completes; restore must lose. Concrete rule needed (D4).

## 5. Smallest Sensible Architectural Foundation

One Gradle module. Four conceptual layers expressed as packages, with dependency direction enforced by convention now and by module extraction later if needed:

1. **Data** — Room (library, favorites, history, playlists, queue snapshot), DataStore (settings), MediaStore data source, sync engine.
2. **Playback** — `MediaSessionService` hosting ExoPlayer; a Kaon-owned **playback facade** exposing immutable `StateFlow` state and intent methods (play, pause, enqueue, playNext, move, remove, seek). UI never touches `MediaController` or `Player` directly.
3. **Feature/UI** — Compose screens + ViewModels, depending on the facade and repositories.
4. **Design system** — tokens (color, type, spacing, shape, motion) and reusable components; theme selection via DataStore.

No use-case layer, no event bus, no plugin infrastructure, no repository interfaces-with-one-implementation. Repositories are concrete classes; `internal` visibility used deliberately; Hilt for wiring.

## 6. Major Boundaries and Dependency Direction

```
feature/*  ──▶  playback facade  ──▶  Media3 (MediaController)
    │                                      │
    └──────▶  repositories  ──▶  Room / DataStore / MediaStore
                   ▲
playback service ──┘  (reads queue snapshot only)
```

Rules:
- **Media3 owns**: current item, position, play/pause state, shuffle/repeat modes, the live queue (timeline), audio focus (`setAudioAttributes(..., true)`), becoming-noisy (`setHandleAudioBecomingNoisy(true)`). Do not write custom focus handling — Media3's is correct and tested.
- **Kaon owns**: favorites, history, playlists, persisted queue snapshot, settings, and UI-derived state (e.g., "is current track a favorite" = combine of player state + favorites flow).
- **Nothing in data depends on UI or playback. Nothing in playback depends on Room except the queue snapshot store.** No cycles.
- **All queue mutations go through granular timeline APIs** (`addMediaItem`, `moveMediaItem`, `removeMediaItem`) — never re-`setMediaItems` the full list after initial set. This is what guarantees "mutations don't restart playback."

## 7. Initial Repository / Module Structure

**One module: `:app`**, packages:

```
kaon.app            Application, MainActivity, Hilt wiring
kaon.core.designsystem   tokens, theme, shared components
kaon.core.playback       MediaSessionService, playback facade, queue snapshot restore
kaon.core.data           db (entities/DAOs), DataStore, MediaStore source, sync engine
kaon.feature.library     tracks/albums/artists screens
kaon.feature.player      mini-player + full player overlay
kaon.feature.search
kaon.feature.playlists
kaon.feature.settings
```

**Why not multiple modules now:** with one developer, modules cost build-config complexity and give you compile-time boundary enforcement you can currently get from discipline. **Extraction triggers** (written down now, honored later): (a) incremental build times become painful, (b) a boundary is actually violated in review, (c) `core.playback` or `core.data` needs isolated testing that the single module impedes. The first extraction candidate, if any, is `core.playback`.

From day one, independent of module count: Gradle version catalog, KSP, **Room schema export directory committed to the repo** (this is what makes future migrations testable — expensive to retrofit, free now), R8 on release builds, and a minimal GitHub Actions workflow (assemble + unit tests) once the first code lands.

Repository root stays conventional: single `app` module, `gradle/libs.versions.toml`, committed `schemas/`. No build-logic module, no convention plugins until a second module actually exists.

## 8. First Architectural Decisions to Settle

### D1 — minSdk

**Decision:** Minimum supported Android version.
**Reasoning:** Blocking. It determines the permission model (legacy storage permission ≤32 vs. `READ_MEDIA_AUDIO` 33+), artwork APIs (platform thumbnails are 29+), and how much version-branching exists in the MediaStore layer. compileSdk/targetSdk are fixed at 36; the floor is unspecified.
**Alternatives:** 26 (Android 8.0) / 29 / 33.
**Trade-offs:** 33 would collapse permissions to one path but excludes exactly the "modest hardware" devices the vision targets. 29 barely simplifies anything — you still carry two permission paths until 33. 26 covers virtually the entire music-playing market at the cost of one isolated legacy-permission branch and one legacy artwork branch.
**Recommendation:** **minSdk 26.** Needs your confirmation — this is your call, not mine.

### D2 — Track identity (the most important decision in this document)

**Decision:** Kaon-owned stable `trackId` (database-generated) keys all user data. MediaStore ID is stored as the *sync match key*, not the identity. Playable URIs are derived at playback time, never stored as identity.
**Reasoning:** "Music belongs to the user" means favorites, history, and playlists must survive renames, moves, and provider rebuilds. MediaStore IDs are *usually* stable but not guaranteed — keying user data to them risks silent rot, which violates the core promise of the app.
**Sync-time rule:** when a stored MediaStore ID vanishes, attempt re-linking before declaring deletion — match candidates on (duration ± tolerance, file size), then (normalized title + artist + album). **Unambiguous single match → re-link** (update stored MediaStore ID). **Ambiguous or none → mark orphaned**, keep the user data, hide from UI, purge after a retention window (~30 days).
**Alternatives:** (a) MediaStore ID as primary key — simplest, fragile; (b) file path — breaks on rename, disqualified; (c) audio fingerprinting/hashing — robust but reads every file, major complexity, no v1 justification.
**Trade-offs:** heuristic matching can misfire on true duplicates (two copies of the same track); the unambiguous-only rule makes misfires rare and non-destructive. Orphan handling adds modest sync complexity.
**Recommendation:** Adopt. If we ever need stronger identity, content hashing can be added as an *additional* match signal without schema upheaval — that's the extension point, and it costs nothing today.

### D3 — Playback state ownership

**Decision:** The Media3 `Player` inside the `MediaSessionService` is the single source of truth for playback. UI talks only to a process-scoped **playback facade** exposing immutable `StateFlow`s and intent methods. Media3 owns focus (`setAudioAttributes(..., true)`) and becoming-noisy (`setHandleAudioBecomingNoisy(true)`) — no custom focus code.
**Reasoning:** Eliminates the dual-state-machine risk you flagged. Centralizing `MediaController` connection in the facade removes the most common real-world Media3 bug class (connection leaks, cold-start races).
**Alternatives:** per-screen controllers (leaks/races); a parallel Kaon playback state store (competing truth — explicitly against your requirements).
**Trade-offs:** the facade is hand-written and could bloat into a god object; countered by a hard rule — it exposes player-derived state and intents only, no library logic.
**Recommendation:** Adopt.

### D4 — Queue persistence

**Decision:** The *service* persists a queue snapshot to Room: ordered track IDs, current index, position, repeat/shuffle modes. Writes are debounced on queue change and flushed on pause/stop. **Restore rule:** on service start, restore only if the player is empty *and* no controller request has started playback — restore always loses to explicit user action. Orphaned tracks are skipped during restore.
**Reasoning:** Queue must survive process death (your requirement); Media3 does not do this for you. The service owns the player, so it owns the snapshot — no second writer.
**Alternatives:** session-state parcelables (not durable across process death); DataStore (wrong tool for a thousand-row list); no persistence (violates requirements).
**Trade-offs:** debounced writes add slight complexity; exact shuffle-order restoration semantics need verification in implementation — the requirement is "reproduce the timeline exactly," validated by tests.
**Recommendation:** Adopt.

### D5 — Library synchronization

**Decision:** **Query-based full reconcile**, run on app start and on `ContentObserver` notification (debounced) while the process is alive. Fetch the full audio projection (ID, path, size, duration, date_modified, title/artist/album/albumId, track number), diff in memory against stored rows, apply only the delta in one transaction. Deletions route through D2's re-linking before orphaning.
**Reasoning:** MediaStore offers no reliable cross-version change journal for audio (`getVersion` is vendor-inconsistent; generation/date deltas are fragile). A full metadata *query* is cheap even at 50k tracks; the *writes* are incremental because only the diff is applied. Idempotency makes interrupted sync recover for free — the next run simply reconciles again. This is the simplest correct design.
**Alternatives:** delta sync via version/generation (fragile); WorkManager-scheduled background sync (unjustified — nothing needs the library fresh while the app isn't running; **trigger to revisit:** a concrete feature that does).
**Trade-offs:** "full query" sounds heavy but isn't; must be verified with a large-library benchmark later (Macrobenchmark or manual), per your measurement principle.
**Recommendation:** Adopt.

### D6 — History schema

**Decision:** Append-only `play_event` table: `id, trackId, eventType (play | skip), playedAt, playedMs`. "Recently played" and "most played" are queries, not tables. No aggregation tables in v1.
**Reasoning:** Past listening is impossible to backfill — this schema must be right in the *first* release, and raw events preserve every future option (aggregates can always be derived; the reverse is impossible). Skip events cost one column and preserve the recommendation signal you listed.
**Trade-offs:** most-played queries scan events; fine at realistic volumes, with the named trigger to add aggregation if measured slow.
**Open sub-decision:** play-count threshold — assumption: record after 30s or 50% played. Confirm or adjust.

### D7 — Artwork

**Decision:** Coil is the only decode/cache pipeline. One internal artwork-source component hides the platform split (`ContentResolver.loadThumbnail` on 29+, legacy album-art path on 26–28). Requests are size-aware: thumbnails for lists, larger for the full player. Failures resolve to placeholders and never propagate to playback or library.
**Reasoning:** repeated full-size decoding is the top memory/jank risk in music apps; sized requests via Coil's caches address it directly. The version split is a genuine platform seam — the one place a small interface is justified.
**Defer:** external artwork providers.

### D8 — Navigation

**Decision:** Adopt Navigation 3 **pending a verification spike before the first screen**; the mini-player/full-player is an app-level overlay, *not* a navigation destination.
**Reasoning:** You prefer it; the destination count is small (~8–10), so the risk is contained and reversible early. The player-as-overlay rule holds regardless of library choice and prevents the back stack from swallowing playback UI.
**Alternatives:** Navigation 2 for Compose (mature fallback); hand-rolled back stack (unjustified custom infrastructure).
**Action item:** verify Nav3's current stability/adoption status — I can check this now if you want. Decide firmly within the first milestone; switching cost grows with screen count.

### D9 — Logging & observability

**Decision:** Timber (or an equivalent thin wrapper) from day one; tagged, verbose logging for playback and sync in debug builds. **No crash reporting in v1** — it conflicts with the privacy identity unless opt-in.
**Open:** whether to add opt-in crash reporting later. Your decision; flagged, not invented.

### D10 — Search

**Decision:** Plain Room `LIKE` queries with case-folded columns in v1. **Trigger for FTS:** multi-token matching, ranking, or measured query slowness. No search engine, no premature indexing infrastructure.

## 9. What Must NOT Influence the Initial Architecture

Explicitly excluded from shaping v1 structure:

- **Plugin/kernel system** — no indirection "for future plugins." If enrichment providers ever land, an interface is introduced *then*, for *that* seam.
- **Streaming** — no local/remote media abstraction. Media3's `MediaItem` already handles arbitrary URIs; that free seam is the only concession.
- **Recommendation engine** — the only concession is D6's event schema, justified on its own merits.
- **Runtime UI customization beyond design tokens** — no layout engines, no downloadable themes, no UI modules.
- **Online services, accounts, cloud sync** — none.
- **Event bus / message-driven architecture** — Flows and direct calls only.
- **Use-case-per-class layer** — ViewModels call repositories/facade directly; a class is extracted only when logic is genuinely shared or complex.
- **Multi-module structure** — per §7, with written extraction triggers.
- **Cross-platform anything.**
